# 编辑器是本地服务加手写前端，esbuild 只负责打包

状态：已接受（2026-09-19）

编辑器要读写使用者磁盘上的 `site.json`、`pages/`、`assets/`，浏览器自己做不到，因此需要一个本地服务；而 `file://` 约束（[ADR-0001](0001-file-protocol-compatible-output.md)）只约束交付产物，不约束编辑器自身。于是：

- 服务端用 Node 内置的 `http`，不引框架，只监听 `127.0.0.1`，默认端口 4173，被占用就往后递推
- 前端是手写的 ES module，不引 UI 框架；esbuild 作为 devDependency 把入口打成一个包，产物不入 git
- 浏览器端不留状态：每次保存都把内存里的指纹交给服务端比对（[ADR-0006](0006-stale-write-guard.md)），不符即拒绝
- 陈旧写入靠每两秒一次的轮询发现，不用 `fs.watch`

## Consequences

- 运行时不新增依赖，工具仓库仍只有构建器与编辑器两块；`npm install` 的体积增量集中在 esbuild 这一个 devDependency
- 轮询最多有两秒的发现延迟，换取跨平台一致（`fs.watch` 在 Windows 与 macOS 上行为不同，还要处理自己写入的回声）
- 这一轮界面简单，所以手写 DOM 划算；下一步换 Milkdown 时打包这条通路已经铺好，动的是 `src/editor/ui/` 里的入口，不是服务端
- 只监听 `127.0.0.1`：这个工具给人自己用，不往局域网暴露

## Considered Options

- **express 或 koa**——为几个接口引一整套框架，运行时依赖变重，且它借宿在一个以零依赖为荣的工具仓库里
- **前端上 React 或 Vue**——这一轮的界面只有导航树与一个源码框，引入框架只是给下一步的 Milkdown 多一层要协调的东西
- **`fs.watch` 即时监听**——跨平台差异大，编辑器自身写入还会造成回声，轮询的确定性更值钱
- **用修改时间判定陈旧**——复制、同步、时钟漂移都会造成虚假变化，内容哈希才是可靠依据
